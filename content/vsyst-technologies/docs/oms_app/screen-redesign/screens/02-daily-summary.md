## 1. Purpose ⛔

- **One sentence:** a dealer user opens one customer's orders — or a customer user opens one dealer's orders — for a start-to-end date-time window (today by default), on two tabs (Purchase, Sales), sees the window's totals in a summary card, narrows by status with the chips the code already knows, scrolls the orders twelve at a time, selects some to see _their_ totals instead, and expands any order to read its products, driver and remarks.
- **Replaces** (all v3, all in `src/screens/Common/DailySummary/`; 2,433 lines):
  - `index.js` (136) — the two-half segment pill (Purchase Orders / Sales Orders, Sales Orders default), the day range held in state (`moment().startOf('day')` → `endOf('day')` on the **device clock**), the header title = `companyName`, the header reset glyph that `navigation.replace('DailySummary', params)`, and the on-focus reset of range + segment.
  - `SalesOrders/index.js` (265) — `useLazyFetch_so_msts_DRQuery` → v3 `POST so_msts/app/section2` (`api_v3/services/so_msts.js:665`, skip/limit + `countDocuments`, page 15), then **client-side** status filtering (default `['DELIVERED']` = not yet invoiced; `INVOICED` = `inv_id || gst_inv_id`) and a client-side re-sort — so a page of 15 can show fewer rows than it fetched.
  - `PurchaseOrders/index.js` (285) — `useLazyFetch_order_so_POSTQuery` → v3 `POST order_msts/a/poso` (`advancedResults.getResults` + `multipleOrderRes`, page 15, `order_status` default `['PENDING','PROCESSING']`), again filtered and re-sorted on the client.
  - `component/index.js` (1,176) — `TotalsCal` (the summary: Petrol litres, Diesel litres, Product Amt = Σ amount − Σ cash reimb, Cash Reimbs — over the **loaded, filtered page**, or over the **selected** rows when any are selected), `OrderStatus` (the five status glyphs), `ListItem` (index, padded number, status glyph, `DDMM HHmm`, vehicle reg no on a yellow wash, amount = products + cash reimb; expanded: products table, cash reimbursement, driver, remarks, the linked PO/SO number), `ListItems` (select-all, the status chips, expand-all, `FlatList` with a **load-more button** in the footer — not infinite scroll).
  - `components.js` (571) — an older copy of the same pieces (`TotalSums`, `TotalSumWQtys`, `DatePicker_Sort`). **Not dead** (found 2026-09-16): `src/screens/Customer/VehicleReports/components.js:36` imports `DS_CashReimbursement` and `DS_Driver` from it, so Step 6 cannot delete the folder wholesale — move those two pieces or retire VehicleReports first.
  - Shared, **not** deleted by this screen: `src/components/DatePicker/DTBS.js` (716 lines; the date-time range sheet — also imported by `src/screens/Common/Reports/DailyReport/index.js`, so it stays).
- **The states, as the code defines them (the user's rule, round 2):**
  - Purchase orders carry `order_msts.order_status` ∈ `PENDING` → `PROCESSING` → `DELIVERED` → `INVOICED` (set on the PO when its sales order is invoiced, `api_v3/services/invs.js:322,491`) · `DELETED` (never listed). v1 chips on the Purchase tab: Pending, Processing, Delivered, Invoiced; default **Pending + Processing**.
  - Sales orders have no stored status: `INVOICED` when `inv_id || gst_inv_id`, else `DELIVERED`. v1 chips on the Sales tab: Delivered, Invoiced; default **Delivered**.
  - Chips are multi-select and **the last selected chip cannot be turned off** (`onSelectOrderStatus`: `if (current.length === 1) return`).
- **Roles:** dealer and customer, one screen. The dealer opens it for a customer, the customer for a dealer. **Nothing differs between the roles except which side of the relation the token supplies** (P‑2).
- **Entry points (params exactly as the callers send them — the v2 Customers exit is already tested against them):**
  - v2 Customers daily tile, `src/screens/v2/Dealer/Customers/index.js:721` → `navigate(PARENT, { screen: 'DailySummary', params: { companyID: row.cust.id, companyName: row.cust.name, ID_FIELD: 'cust_id' } })`
  - v1 Customers, `src/screens/Dealer/Customers/index.js` → same route, same three params
  - customer-side Dealers, `src/screens/Customer/Dealers/index.js:334` → `navigate('customerDealer', { screen: 'DailySummary', params: { companyID: item.dealer_id._id, companyName: item.dealer_id.dealer_name, ID_FIELD: 'dealer_id' } })`
  - The v2 screen **accepts all three params unchanged** and reads only `companyID` and `companyName`; `ID_FIELD` is redundant once the role comes from the token (P‑2) and is ignored, not refused.
- **Exit points:** none (A‑6, recommended). v1 has none; a v2 row's expanded body **is** the detail. The refresh glyph never rebuilds the route (P‑9).

### 2c. Theme, language, text scale and weight — cross-cutting rules (the user, round 3)

**Colours come from the app's theme, never from the frames** (user: "we use color theme from app not the screenshot. screenshot is only for design and layout reference. we use our colors instead"). Nothing new is minted for this screen; the frame's purple gradient, green, blue and yellow map onto roles that already exist, and every colour in code and in tests is the token (ESLint refuses a literal in v2; `src/theme/__tests__/eslintRule.test.js`):

**Hindi (F-APP-10).** `strings.js` + `strings.hi.js` key for key (the completeness test), every word through `useStrings(table)`, the header title is the company's NAME from the route param in both languages (a name is not translated) and is still set from the screen via `headerTitle` so the navigator's string cannot win (the F-APP-10 lesson), with a strings fallback only when the param is missing; the two header tabs and the chips looked up by key, Devanagari line height through `AppText` (`SCRIPT_LINE_HEIGHT.hi` = 1.2 in `src/theme/scale.js`), the `Screen` key `fs:${fontScale}:${language}` remounting on a live change, Android Devanagari tails already handled app-wide (`AppTextView` theme, `useBoundsForWidth=false`). Chip and tab labels change only with the language, never with state, so no ghost-word width lock is needed (decision 72's amendment does not apply). Tests: `withLanguage('hi', …)` per component, `renderScreen(ui, { language: 'hi' })` for the screen — the header reads the Hindi title, the tabs, chips, captions and empty strings are Hindi, money and vehicle numbers unchanged.

**Enlarged text (F-APP-7, "text sets the box").** No `height` on anything that holds text; `minHeight` and padding come from the type role through `useTypeScale()`; digits never wrap; glyphs, hairlines and the 44 pt targets do not scale. The test points are 1 / 1.353 / 2.143 (iOS AX-L; Android 200 % is 2.0 and sits under the same rule). **P‑14 — what yields, per element, all width-driven (`contentWidth` vs `fontScale`, the `tilesStack` idiom in `layout.js`), never a fixed breakpoint:**

| Element      | Fits                                          | Does not fit                                                                                                                                 |
| ------------ | --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| header tabs  | two words in the header's right slot          | the tabs drop to their own row under the header (measured, decision 73's `onLayout` idiom); the title keeps the header                       |
| date range bar (P‑18) | glyph · name · window on one line between the two steppers | the print retreats by a measured rule — the name over the window (two lines), then the glyph gives up its room, then the window breaks at the arrow; the two 44 pt steppers never move |

| control row  | check · chips · Expand on one line            | the chips wrap onto a second line under the check; the check and Expand keep their slots (a wrapping row, as decision 73's sort row)         |
| row          | number + glyphs line, date + vehicle + amount | the vehicle pill wraps under the date; the amount takes its own line, right-aligned, never ellipsised; the running index stays in its gutter |
| panel        | the panel scrolls; the pane's rows as above   | the panel is a `ScrollView`, so nothing in it is ever clipped; the pane's rows fall back as the phone's                                      |

Each cell is a Tier 3 case at 1.353 and 2.143 on `PHONE`, plus 2.143 on `PHONE_SIDE` (the panel) and `TABLET` (`medium/tall`).

**Bold Text (the OS accessibility weight).** iOS raises the weight and measures it — nothing to do beyond the rule above. Android applies it as `fontWeightAdjustment` and RN measures the _un-bolded_ width (`docs/testing.md`, the recorded limitation), so the rule that holds this screen is the one from [[../06-all-screen-shapes-plan|06]]: **no fixed-width text slot anywhere** — pills, chips, tabs and captions size to content with `flexShrink`, no `width` on a text container, no `numberOfLines` on a value, the row's amount on a line of its own when it must be. Jest cannot switch Bold Text on, so this is a **device-only** check: the checklist runs Android Bold Text ON at 1× and 200 % (Pixel Fold AVD or the real phone) and iOS Bold Text ON at 1× and AX-L, and logs the result in the runbook's "Device runs". A tail that still clips under Android Bold Text is the RN limitation, recorded, not a screen defect.

### Proposed decisions (P‑n) — each becomes a test name

1. **P‑1 One read model per tab, not both lists per request.** `POST /api/v4/screens/daily-summary` returns the active tab's page + the active tab's summary. Two paged lists in one envelope would need two cursors and would double every page's payload for a tab the user is not looking at; switching tabs is one request, and RTK Query caches each tab's key separately. (Closes Q2.)
2. **P‑2 The role decides the side of the relation; the body carries only the counterparty.** Body `companyId` is the customer for a dealer bearer and the dealer for a customer bearer; `scopeFilter(req)` pins the caller's side, `assertRelation({ dealer_id, cust_id })` refuses a pair the caller is not in (403, one indexed lookup). No `idField`, no `dealer_id`/`cust_id` keys — sending one is a 400 unknown key. (Closes Q1's "different pieces?": none.)
3. **P‑3 The default window is the server's IST calendar day.** `range` omitted ⇒ the server uses the IST day of now from the same `ledger_window.js` arithmetic the Customers daily tile uses, and echoes it in `meta.range` with `rangeSource: "default"`. The phone shows the same window from a pure helper (fixed +05:30, no library) before the response arrives and adopts `meta.range` when it lands. Once the user touches either pill both instants are sent explicitly (`rangeSource: "body"`). (Closes Q3; the O‑3 parity test pins it.)
4. **P‑4 The status chips are v1's, applied on the server, and the card follows them.** Per tab exactly the sets, defaults and "last one stays on" rule in §1 (the user's rule: states as in the code). `filters.status[]` goes in the body; the page query and the summary aggregate share the filter, so a page is always 12 full rows (v1 filtered a page _after_ fetching it and could show 3 of 15) and the card is the total of what the chips admit — the Customers rule "totals follow the filter". `DELETED` is never listed and is not a chip. The frames' un-filled chips are reference only.
5. **P‑5 Sort is fixed: `on_dt` desc, ties `_id` desc; keyset cursor from `lib/cursor.paginate`.** Exactly the seek `lib/cursor` already implements (`{ k: on_dt, _id }`, `t: "date"`); `PAGE_SIZE = 12` is an endpoint constant like Customers — no `limit` key.
6. **P‑6 Selection and expansion belong to one list.** Both sets are keyed by the request key (body minus cursor): a new tab, range or chip set empties them and the list opens at the top (decision 65 pattern); a load-more keeps them; a refresh prunes them to ids still present. Select-all = the loaded rows. A tab switch also resets the chips to the new tab's default (v1 keeps per-tab chip state in each sub-list; same effect).
7. **P‑7 Expanding is free.** Each row carries its products, driver, remarks and linked number; the phone never fetches to expand. One request per page, full stop.
8. **P‑8 The card's selection mode is a pure client sum of row fields.** `selectionTotals(rows, selectedIds)` adds the rows' `qty.petrol`, `qty.diesel`, `productAmount`, `cashReimb`. The invariant the fixture test pins: `selectionTotals(allRowsOfAllPages, everyId)` **equals** `summary` — true only if the server computes the row numbers and the totals with one formula, so the rule is "the phone never recomputes from `products[]`".
9. **P‑9 Refresh = scroll-to-top + refetch, never `navigation.replace`.** Customers decision 65. Re-focus refetches the current query; it does **not** reset the range, the tab or the chips (v1 did, because its state lived outside the route). A new `companyID` in the route params remounts the model with defaults (the `Screen` key gains `companyID`). The glyph lives in the range row / the panel header (D‑2), not in the navigator header. (Closes Q4.)
10. **P‑10 A row with a missing vehicle or driver is a row with `null`, not a failed page.** v3 throws 404 for the whole list when one `veh_id` dangles; v4 shapes `vehicle: null`.
11. **P‑11 The summary rides on list-defining requests, not on load-more (revised round 5, A‑8).** A request without a `cursor` (first load, tab, range, chips, refresh) returns `summary` + page 1; a request with a `cursor` returns the next page only. The read model skips the aggregate when a cursor is present; the phone's cache keeps the page-1 `summary` across appended pages and replaces it on any non-cursor response. The user's rule in one line: _scrolling never changes the totals; selecting changes `n` and the amounts on the phone; filters change everything._

**Window semantics — one inclusive rule everywhere:** the filter is `on_dt: { $gte: from, $lte: to }` for both the default and a body range. The default window is `[istDayStart(now), istDayEnd(now) − 1 ms]` — `istDayEnd` (`ledger_window.js:67`) is the first instant of the _next_ IST day, so one millisecond is taken off to keep the ceiling inclusive — and `meta.range` echoes exactly those two instants. v1 and the Customers tile both use an inclusive `$lte` on the picker's end-of-day; the day-boundary test in §5.3 pins it.

**Status filter semantics (as the code):** `po` → `order_status: { $in: applied.status }` (`DELETED` can never be in the list, so it is excluded by construction); `so` → `DELIVERED` = `{ inv_id: { $in: [null, absent] }, gst_inv_id: { $in: [null, absent] } }`, `INVOICED` = `$or: [inv_id exists, gst_inv_id exists]`, both = no invoice condition. One pure `statusMatch(tab, applied)` builds the clause and is unit-tested; the page query and the aggregate both spread it.
