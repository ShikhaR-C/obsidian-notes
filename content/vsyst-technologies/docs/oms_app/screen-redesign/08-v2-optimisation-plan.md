## 1. Rules for the whole job

1. **No behaviour change** except the items marked _behaviour_ (RT‑1, RT‑2, the API items the user approves). A refactor is proved by the **existing tests passing untouched**; a test file changes only when a module it imports has moved, never to loosen an assertion.
2. **Behaviour items are test-first** (red commit, green commit). Refactors are single `refactor(...)` commits. Comment-only work is `docs(...)`.
3. **Every testID stays.** They are the contract the **111 suites / 2777 tests** hold.
4. **v2 guards hold**: no colour literals, no JSX text literals, words through `useStrings` (en + hi), sizes from the type scale. Colours in code **and in tests** come from theme tokens, never a hex.
5. **v1 files are not touched** (`DTBS` included — no v2 screen mounts it any more; v1's Daily Summary and Reports still do).
6. **One file at a time in the comment pass, suite run after each** — nine test files read source text; §7 lists the files whose comments are policed.
7. Builders leave the tree uncommitted and report; the user is shown the diff before any commit. No push, no merge.
8. After each wave: full suite, ESLint on the touched folders, and the Android emulator at **320 dp (the baseline: the designed arrangement holds there at 1×, English and Hindi)**, 360 dp and the panel.
9. **Build evidence stays on the build machine** — red-test logs and device screenshots are never committed, and no committed file or PR body points at them.

## 6. App — the comment standard (CM‑n)

**CM‑1 The standard.**

1. **File header: 2–5 lines.** What the file is; one line per arrangement if it has more than one.
2. **Every exported function, component and hook: a JSDoc block** — one sentence, then `@param {type} name - meaning` (units: dp, pt, paise, ms), then `@returns`.
3. **Every exported constant: one line** — what it is and its unit.
4. **Inline `//`: only where the code is surprising** — a platform quirk, a deliberate wrong-looking choice. One line; if it needs two it belongs in the runbook.
5. **Decisions are referenced, never retold:** `(decision 72)`, `(P‑17)`, `(decision 41)`.
6. **Not in code:** dates, quotes, "there used to be…", device anecdotes, ASCII rules, paragraphs over four lines. Block comments rather than trailing `//` (three of the source-reading tests strip only line-leading `//`, and four strip nothing — §7).

**Where the tree stands against it (2026-09-21):** `@returns` — **0**; `@param` — **17**, 16 of them in `ControlRow.js:77–82, 118–122, 159–171`, which is the one file already written to rule 2's shape and the model to copy. **The date range tree (4,031 lines, written after this standard was proposed) did not adopt rule 2 and breaks rule 6 at scale** — it is the comment pass's first target.

## 8. API — findings and proposed changes (API‑n)

> **Re-checked 2026-09-21: no commit on `api_screen_daily_summary` since `e996355`** — every finding, line and proposal below stands as written on 2026-09-17. What changed is the **weight**, from the app's side: a long window used to take two pickers and four taps, so the page and the summary mostly saw one day. **"Last 7 days" and "This month" are now one tap and Done** — a whole calendar month of a busy relation through a page query no index can serve (F‑1) and a summary with no time limit (F‑2). **API‑1 and API‑3 are no longer "at production size" concerns; ordinary use reaches them.** In the other direction the app got lighter: one request per Done (v1's picker sent one per end — a 6–6 day cost two), none while the user is choosing, and a phone that remembers 6 - 6 AM sends its range on the **first** request rather than a default then a correction.

**The short answer: the network side is already right; the database side is not.** Each screen opens with **one POST**; a page of 12 is ~1 KB gzipped (compression is on); parsing it costs a low-end phone under 0.2 ms; on a 100 kbps / 400 ms link a page takes ~0.5 s, of which 0.4 s is the round trip. **What a user on any phone will wait for is the query time on the server** — and at production size (a dealer with 2,000 customers and 300,000 orders, a relation with 20,000) several reads scan far more than they return. Every claim below was checked against `models/*.js` and the read models.

### 8d. Deliberately not changing

- **The payload.** The app reads nearly every field; deleting all the unread ones (`success`, `orders[].kind`, `vehicle.id`, `products[].category / inputType / isFullTank`, four `meta` keys) saves 980 B raw but **99 B gzipped — 8 ms at 100 kbps**. Not worth a contract change.
- **Row details on the row (P‑7).** Fetching them on expand would save 340 B gzipped per page (27 ms) and cost **+400 ms per expand**. The current design is the right one for a slow link.
- **The range on the wire.** Two instants, `to` the last millisecond inside; the date range sheet changed the phone, not the contract.
- Keyset pagination with `limit + 1`, no `countDocuments`, no `skip`; constant round trips pinned by tests; no N+1 (every join is an `$in` or a group by `cust_id`); `.lean()` and explicit projections everywhere; integer money **inside** the pipeline; tenancy from the token; A‑8 (summary only on list-defining requests); compression mounted first.
