## Q0. For each capability: what it is, when it arrived and what iOS 26/27 changed, the native building blocks, how React Native integrates it, and how a petroleum-dealer OMS would use it

### Takeaway
Everything on the list is reachable from this React Native 0.84.1 app, but it splits three ways: (1) in-process UI features (share sheet, document picker, Quick Look, camera/photo picker/scanner, maps, biometrics, passkeys, in-app messages) already wrapped by maintained New-Architecture libraries; (2) system surfaces that run outside the app process — App Intents/Siri/Spotlight, widgets, Controls, Live Activities, Notification Content Extensions, App Clips — which always need Swift types compiled into the app or into an extension target, with JavaScript at most feeding data via an App Group, a shared Keychain item, or a bridge; (3) iOS 26/27-only APIs (interactive snippets, Visual Intelligence, `BGContinuedProcessingTask`, `RecognizeDocumentsRequest`, `LongRunningIntent`, App Intents Testing) with no React Native wrapper found, so a small team-owned Swift TurboModule is the route. iOS 27 also moves the ground under every feature: the UIScene life cycle is mandatory with the iOS 27 SDK (this app already has a SceneDelegate), the Liquid Glass opt-out key is ignored when building for iOS 27, and "portrait-only" becomes a preference that resizable environments ignore.

#### 1 · App Intents + Siri + Apple Intelligence + Shortcuts + Spotlight
**What the user sees:** the app's actions and records show up in Siri ("Hey Siri, what's my outstanding balance in DZZLO"), in the Shortcuts app, in Spotlight results, on the Action button, in widgets/Controls, and — on Apple Intelligence iPhones with iOS 27 — as tools Siri AI can call from free-form requests, with answers shown as (interactive) snippets.

#### 2 · Live Activities + Dynamic Island (ActivityKit + WidgetKit extension)

#### 5 · App Clips
**What the user sees:** a card slides up after scanning a QR/App Clip Code, tapping an NFC tag, a Safari Smart App Banner, a Maps place card or a Messages link; one tap runs a small slice of the app without installing it; the system later deletes it.
- `APActivationPayload` (App Clip framework) iOS 14.0 — [Apple docs](https://developer.apple.com/documentation/appclip/apactivationpayload) ✅. App Clips "don't appear on the Home screen … the system removes an App Clip from a device after a period of inactivity" — [App Clips](https://developer.apple.com/documentation/appclip) ✅.
- Size (uncompressed): 10 MB (iOS 15 and earlier); 15 MB (iOS 16); 100 MB (iOS 17+) only when the clip supports digital invocations only (no App Clip Codes, QR codes or NFC tags), targets iOS 17+ only and expects a reliable connection; the App Store Connect demo link allows 100 MB — [Choosing the right functionality for your App Clip](https://developer.apple.com/documentation/appclip/choosing-the-right-functionality-for-your-app-clip) ✅.

- Target: bundle ID = full app ID + `.Clip`; entitlements `com.apple.developer.on-demand-install-capable`, `com.apple.developer.parent-application-identifiers`, `com.apple.developer.associated-appclip-app-identifiers` (added by Xcode) — [Creating an App Clip with Xcode](https://developer.apple.com/documentation/appclip/creating-an-app-clip-with-xcode) ✅. Website association uses the associated domain `appclips:<fully qualified domain>` — [Associating your App Clip with your website](https://developer.apple.com/documentation/appclip/associating-your-app-clip-with-your-website) ✅.
- Invocations: App Clip Code, NFC tag or QR code at a physical location; a link in Maps; a Smart App Banner in Safari or `SFSafariViewController`; an App Clip card in Safari/iMessage; a link shared in Messages (text messages only); an App Clip preview or link in another app (iOS 17+); a link in email or on a website. ### Inferences

**How an App Intent reaches — or does not reach — React Native JavaScript**
- The system may run an intent's Swift `perform()` while the app is cold, backgrounded, or (iOS 27 `ExecutionTargets`) inside an App Intents or widget extension, and Apple's own test framework runs intents "out-of-process"; the RN runtime is therefore never guaranteed to exist. Questions that need an answer now ("what is my outstanding balance?") must be answered in Swift: either call the API directly with `URLSession` using an auth token the app stores in a Keychain item shared through `keychain-access-groups`, or read a JSON snapshot that JS writes into the App Group container. `expo-app-intents`' model (persist the invocation, deliver it to JS when JS is listening; "remain pending" while closed) suits "do something in the app" intents, not synchronous answers.
- Intents that should open the app (iOS 26 `supportedModes` with a `.foreground(…)` mode; `OpenIntent` on older systems) can hand off to JS through a URL that the RN `Linking` handler already understands (the app already declares `CFBundleURLTypes`).
- The deployment target is iOS 15.1, below every system-surface API here (App Intents 16.0, Live Activities 16.1/17.2, interactive widgets 17, Controls/IndexedEntity 18, SnippetIntent/`BGContinuedProcessingTask`/`RecognizeDocumentsRequest` 26, `LongRunningIntent`/App Intents Testing 27). Each feature must be `@available`-gated with a fallback, or the target raised; that is a product decision for the team.

## Q1. Which capabilities can be driven entirely from JS through a maintained, New-Architecture-ready library, and which unavoidably need a Swift extension target the team owns?

### Takeaway
JS-only (maintained, New-Arch, no extension target): share sheet, document picker/export and Quick Look, camera/QR/document scanning, photo picking, image compression, maps, foreground location, Keychain + biometric lock, passkeys, and OneSignal-driven interruption levels, threads, badges and in-app messages. The clauses that bite this app are: 5.1.1(ii) purpose strings (the three generic location strings fail the "clearly and completely" bar), 5.1.1(iii) data minimisation and 5.1.5 location, 2.5.4 background modes, 2.5.14 camera consent, 4.5.4 marketing pushes (explicit in-app opt-in and opt-out) and 4.5.3 (no spam via push or Live Activities), 2.5.16 (widgets, extensions and notifications tied to the app; every App Clip feature also in the main app; no ads in clips), 2.5.11 (Siri/Shortcuts intents), 2.5.15 (Files), 4.4 (extensions: no marketing or IAP), 3.1.3(c)/(e)/(f) for web-billed B2B subscriptions and physical-goods orders, 4.8 (not triggered by OTP login), 5.1.1(v) account deletion, 5.1.1(ix) regulated financial services, 2.5.1 (phase out deprecated tech) and 2.5.13 (LocalAuthentication). No guideline was found that names App Intents/Siri AI beyond 2.5.11, or Live Activities beyond 4.5.3.

### Cited Findings
All quotes from the [App Store Review Guidelines](https://developer.apple.com/app-store/review/guidelines/) as fetched 2026-09-29 (no last-updated date was visible on the page):
- 2.5.1: "Apps may only use public APIs and must run on the currently shipping OS … make sure you phase out any deprecated features, frameworks or technologies that will no longer be supported in future versions of an OS."
- 2.5.4: "Apps may only use background services for their intended purposes: VoIP, audio playback, location, task completion, local notifications, etc."
- 2.5.11 SiriKit and Shortcuts: "(i) Apps integrating SiriKit and Shortcuts should only sign up for intents they can handle without the support of an additional app and that users would expect from the stated functionality … (ii) Ensure that the vocabulary and phrases in your plist pertains to your app … Aliases must relate directly to your app or company name and should not be generic terms … (iii) Resolve the Siri request or Shortcut in the most direct way possible and do not insert ads or other marketing between the request and its fulfillment."
- 2.5.13: "Apps using facial recognition for account authentication must use LocalAuthentication (and not ARKit or other facial recognition technology) where possible…"
- 2.5.14: "Apps must request explicit user consent and provide a clear visual and/or audible indication when recording, logging, or otherwise making a record of user activity. This includes any use of the device camera…"
- 2.5.15: "Apps that enable users to view and select files should include items from the Files app and the user's iCloud documents."
- 2.5.16: "Widgets, extensions, and notifications should be related to the content and functionality of your app. (a) Additionally, all App Clip features and functionality must be included in the main app binary. App Clips cannot contain advertising."
- 3.1.1: features must be unlocked with in-app purchase; apps "may not use their own mechanisms to unlock content or functionality, such as license keys … QR codes…".
- 3.1.3 intro: apps in this section "cannot, within the app, encourage users to use a purchasing method other than in-app purchase, except for apps on the United States storefront and as set forth in 3.1.1(a) and 3.1.3(a)." (c) Enterprise Services: "If your app is only sold directly by you to organizations or groups for their employees or students … you may allow enterprise users to access previously-purchased content or subscriptions. Consumer, single user, or family sales must use in-app purchase." (e) "If your app enables people to purchase physical goods or services that will be consumed outside of the app, you must use purchase methods other than in-app purchase…" (f) Free stand-alone companion apps to a paid web tool need no IAP "provided there is no purchasing inside the app, or calls to action for purchase outside of the app."
- 4.4: extensions "should include some functionality, such as help screens and settings interfaces where possible … and the extensions may not include marketing, advertising, or in-app purchases."
- 4.5.3: "Do not use Apple Services to spam, phish, or send unsolicited messages to customers, including Game Center, Push Notifications, Live Activities, etc."
- 4.5.4: "Push Notifications must not be required for the app to function, and should not be used to send sensitive personal or confidential information. Push Notifications should not be used for promotions or direct marketing purposes unless customers have explicitly opted in … via consent language displayed in your app's UI, and you provide a method in your app for a user to opt out…"
- 4.8: apps using a third-party or social login for the primary account "must also offer as an equivalent option another login service" limiting data to name and email, allowing email to stay private, and not collecting interactions for advertising without consent.
- 5.1.1(ii): "Ensure your purpose strings clearly and completely describe your use of the data." (iii) "Apps should only request access to data relevant to the core functionality of the app…" (iv) do not "manipulate, trick, or force people to consent to unnecessary data access." (v) "If your app supports account creation, you must also offer account deletion within the app." (ix) "Apps that provide services in highly regulated fields (such as banking and financial services …) or that require sensitive user information should be submitted by a legal entity that provides the services, and not by an individual developer."
- 5.1.2: "You must clearly disclose where personal data will be shared with third parties, including with third-party AI, and obtain explicit permission before doing so."
- 5.1.5: "Use Location Services in your app only when it is directly relevant to the features and services provided by the app … Ensure that you notify and obtain consent before collecting, transmitting, or using location data."
- Adjacent submission rules: App Store Connect rejects apps whose required-reason API use is undeclared (since 2024-05-01) — [Apple](https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api) ✅; iOS 26 SDK minimum since 2026-04-28 — [Apple News](https://developer.apple.com/news/?id=ueeok6yw) (search summary); social-media capability declaration for new versions from September 2026 — [WWDC26 App Store guide](https://developer.apple.com/wwdc26/guides/app-store/) ✅; critical alerts need Apple's approval — [Kulman](https://blog.kulman.sk/using-critical-alerts-on-ios/) (secondary).
- This app's location strings all read "$(PRODUCT_NAME) needs Location access for good user experience!" while no location code exists and the `OneSignalLocation` subspec is linked — [Info.plist](/Users/shikhar/Documents/KIT/GITHUB/DZZLO_OMS/v1_79/dzzlo_oms_app/ios/dzzlo_oms_app/Info.plist), [Podfile.lock](/Users/shikhar/Documents/KIT/GITHUB/DZZLO_OMS/v1_79/dzzlo_oms_app/ios/Podfile.lock).

## Q3. What are the effort, maintenance costs and platform prerequisites for each?

### Takeaway
Cheap (≤ 1 week each, est.): share/export/Quick Look, biometric lock, OneSignal interruption levels/threads/badges/in-app messages, quick actions, a customer map, camera/QR scanning. Medium (1–3 weeks, est.): native PDF/print module, first widget with App Group plumbing, Live Activities via OneSignal, a starter set of App Intents with App Shortcuts and Spotlight entities, document scan + OCR, background upload, App Attest. Large (3–6+ weeks with ongoing cost, est.): an App Clip, live tanker tracking, passkeys with server WebAuthn, schema-level Siri AI work. Each new target adds an App ID, a provisioning profile, an entitlements file, often an App Group and a privacy manifest, a Podfile target if it links pods, TestFlight checks, and a yearly WWDC migration pass. Expo-based generators add a React Native upgrade (≥ 0.85) and the `expo` package.

### Cited Findings
- Extension bundle IDs must use the host's bundle ID as a prefix (shown for a widget extension inside an App Clip) — [Apple](https://developer.apple.com/documentation/appclip/offering-live-activities-with-your-app-clip) ✅; App Clip bundle ID = app ID + `.Clip` with three App Clip entitlements — [Apple](https://developer.apple.com/documentation/appclip/creating-an-app-clip-with-xcode) ✅.
- App Groups are registered on the developer website (Apple guarantees uniqueness) and double as keychain access groups — [Apple](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.application-groups) ✅.
- Live Activity push uses token-based APNs; broadcast channels are enabled outside Xcode — [Apple](https://developer.apple.com/documentation/activitykit/starting-and-updating-live-activities-with-activitykit-push-notifications) ✅; `.p8` key required — [OneSignal](https://documentation.onesignal.com/docs/en/cross-platform-live-activity-setup) ✅. - Sequencing that minimises risk (inference): do the in-process items first (share/export/PDF/notification levels), then one widget target to establish the App Group + provisioning pattern, then reuse that target for Live Activities and Controls, then App Intents (which the widgets' buttons also need). Keep App Clip and tanker tracking behind a separate go/no-go because they carry the largest review and maintenance cost.
- A paid Apple Developer Program membership is evidently already in place (the app ships push with an `aps-environment` entitlement); each new target's App ID and profile can be generated by Xcode automatic signing, but App Groups, push keys, broadcast channels and App Clip experiences are account-level set-up steps the account holder must do.
- Choosing Expo-generated targets trades Swift maintenance for an RN upgrade plus exposure to Expo's release cadence (alpha packages break often); choosing hand-written SwiftUI keeps RN 0.84 but puts SwiftUI skills on the critical path.
