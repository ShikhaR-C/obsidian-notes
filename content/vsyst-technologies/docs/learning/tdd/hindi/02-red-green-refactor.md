# 2. Red, Green, Refactor

यही चक्र है। तीन कदम, हमेशा दोहराए जाने वाले, और हर कदम छोटा।

```
   ┌─────────────────────────────────────────┐
   │                                         │
   ▼                                         │
🔴 RED          →     🟢 GREEN     →    🔵 REFACTOR
```

---

## 🔴 RED — एक फेल होता टेस्ट लिखें

ऐसे व्यवहार के लिए एक छोटा टेस्ट लिखें जो अभी मौजूद ही नहीं है। उसे चलाएँ। **उसे फेल होते देखें।**

```python
def test_empty_cart_costs_nothing():
    assert Cart().total() == 0
```

अभी तो `Cart` है ही नहीं, इसलिए यह टेस्ट फट जाएगा। यही तो मक़सद है।

### फेल होते देखना क्यों ज़रूरी है

यही वह कदम है जिसे लोग छोड़ देते हैं, और यही सबसे ज़्यादा फ़ायदा देता है। जिस टेस्ट को आपने कभी फेल होते देखा ही नहीं, उस पर भरोसा नहीं किया जा सकता। हो सकता है वह कुछ टेस्ट कर ही न रहा हो। हो सकता है assertion में typo हो। हो सकता है test runner उस फ़ाइल को उठा ही न रहा हो।

**फेल होने का संदेश भी देखें।** क्या वह साफ़ है? क्या शुक्रवार शाम चार बजे किसी साथी को वह बता पाएगा कि क्या गड़बड़ हुई? अगर संदेश `AssertionError: False is not True` जैसा है, तो टेस्ट अभी सुधार लीजिए — यह संदेश आपको सालों तक पढ़ना है।

> 🔑 **नियम:** जब तक कोई फेल होता टेस्ट माँग न कर रहा हो, तब तक production code मत लिखिए।

---

## 🟢 GREEN — पास कराइए, सबसे बुद्धू तरीक़े से

_सबसे कम_ कोड लिखिए जिससे टेस्ट हरा हो जाए। सुंदर वाला नहीं। सामान्य (general) वाला नहीं। शर्मनाक वाला भी चलेगा।

```python
class Cart:
    def total(self):
        return 0
```

हाँ, यह hardcoded है। हाँ, यह "ग़लत" है। पर यह **हरा** भी है, और इस कदम का यही लक्ष्य है।

### "पर यह तो बेईमानी है!"

नहीं है, और TDD का यही हिस्सा सबसे उल्टा लगता है। यह hardcoded return ईमानदार है: आपकी test suite फ़िलहाल इतनी ही माँग कर रही है। अगला टेस्ट और माँगेगा, और तब यह नक़ली जवाब ख़ुद-ब-ख़ुद बाहर हो जाएगा।

इसका एक नाम है: **triangulation**। एक उदाहरण से आप नक़ल कर सकते हैं। दो-तीन उदाहरण असली logic को उभरने पर मजबूर कर देते हैं।

यहाँ अनुशासन यह है कि जो कोड आप _कल्पना_ में सोचते हैं कि लगेगा, उसे लिखने से बचें। अटकलों वाला कोड ही बग और बेकार वज़न की जड़ है।

---

## 🔵 REFACTOR — सफ़ाई कीजिए

अब जब टेस्ट हरे हैं, कोड को बेहतर बनाइए — बिना यह बदले कि वह करता क्या है।

- दोहराव हटाइए (production code **और** टेस्ट, दोनों में)
- अब जब चीज़ें बेहतर समझ आ गई हैं, नाम बदलिए
- कोई function अलग निकालिए, बेकार परत हटाइए, किसी conditional को आसान कीजिए

हर बदलाव के बाद टेस्ट चलाइए। वही आपकी सीट-बेल्ट हैं — यही वह पल है जब वे अपनी क़ीमत वसूल करते हैं।

### Refactoring के नियम

1. **सिर्फ़ हरे पर refactor करें।** टेस्ट फेल होते हुए ढाँचा कभी मत बदलिए; पता ही नहीं चलेगा कि किस बदलाव ने क्या तोड़ा।
2. **नया व्यवहार मत जोड़िए।** अगर नई कार्यक्षमता जोड़ने का मन हो, तो रुकिए — वह एक नया RED है।
3. **टेस्ट को भी refactor कीजिए।** टेस्ट कोड भी असली कोड है। उसे production code से ज़्यादा बार पढ़ा जाता है।

Refactoring वैकल्पिक नहीं है। इसे लगातार छोड़ते रहिए और आपको ऐसा codebase मिलेगा जो अपने सारे टेस्ट पास करता है और जिसमें काम करना कष्टदायक है।

---

## एक फेरा कितना बड़ा हो?

**मिनटों का।** आदर्श रूप से दो से दस मिनट। अगर पूरा चक्र पूरी दोपहर ले रहा है, तो आपका टेस्ट बहुत महत्वाकांक्षी था — उसे तोड़िए।

एक काम की जाँच: अगर आप ~15 मिनट से ज़्यादा लाल हैं, तो पिछले हरे पर लौट जाइए और छोटा निवाला लीजिए। ऐसा लगता है जैसे किया-कराया गया, पर आमतौर पर यह तेज़ रास्ता है।

## लय

एक बार समझ आ जाए तो यह ऐसा लगता है:

```
fail → pass → tidy → fail → pass → tidy → fail → pass → tidy
 30s    2m     1m     45s    3m     0m     20s    1m     2m
```

छोटा, कसा हुआ, बिना नाटक के। आप कभी भी चलते हुए कोड से दो-चार मिनट से ज़्यादा दूर नहीं होते, जिसका मतलब है कि आप कभी किसी रहस्य को debug नहीं कर रहे होते — बदला तो सिर्फ़ वही है जो आपने अभी टाइप किया।
