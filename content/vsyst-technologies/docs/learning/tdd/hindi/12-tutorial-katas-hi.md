# 12. ट्यूटोरियल — अभ्यास katas

**Kata** एक छोटी समस्या है जिसे आप बार-बार हल करते हैं ताकि मांसपेशी-स्मृति बने। लक्ष्य हल नहीं है — वह तो पहली ही कोशिश में पता चल जाएगा। लक्ष्य है **लय**: red, green, refactor, छोटे कदम, कोई शॉर्टकट नहीं।

नीचे हर kata **चरणों (phases)** में बँटा है, और हर चरण क्रमांकित **steps** में। इन्हें क्रम से कीजिए; ये कठिन होते जाते हैं।

> **हर kata के नियम**
>
> 1. फेल होते टेस्ट के बिना production code कभी मत लिखिए।
> 2. पास कराने से पहले हर टेस्ट को फेल होते देखिए।
> 3. _सबसे बुद्धू_ कोड लिखिए जो पास करा दे। Hardcoding की छूट है।
> 4. Refactor सिर्फ़ हरे पर।
> 5. अगर 15+ मिनट से लाल हैं, तो वापस लौटिए और छोटा कदम लीजिए।

## Kata 1 — FizzBuzz

**कठिनाई:** ★☆☆☆☆ · **समय:** 15 मिनट · **क्या सिखाता है:** शुद्ध चक्र, triangulation

_3 के गुणकों पर `"Fizz"`, 5 के गुणकों पर `"Buzz"`, दोनों के गुणकों पर `"FizzBuzz"`, वरना संख्या को string के रूप में लौटाइए।_

### चरण 1 — सबसे मामूली मामला

1. 🔴 `test_one_returns_1` लिखिए जो `"1"` की अपेक्षा करे। चलाइए। फेल होते देखिए।
2. 🟢 `return "1"` से पास कराइए। हाँ, सचमुच।
3. 🔵 साफ़ करने को कुछ नहीं।

### चरण 2 — नक़ल को बाहर कीजिए

1. 🔴 `test_two_returns_2` जोड़िए।
2. 🟢 Hardcoded `"1"` मर जाता है। `return str(n)` लिखिए।
3. 🔵 अब भी साफ़।

### चरण 3 — Fizz

1. 🔴 `test_three_returns_fizz`।
2. 🟢 `if n % 3 == 0` वाली शाखा जोड़िए।
3. 🔴 `test_six_returns_fizz` — पुष्टि करता है कि आपने नियम लिखा, कोई विशेष मामला नहीं।

### चरण 4 — Buzz, फिर FizzBuzz

1. 🔴🟢 चरण 3 को 5 → `"Buzz"` के लिए दोहराइए।
2. 🔴 `test_fifteen_returns_fizzbuzz`। अगर आपने शाखाएँ ग़लत क्रम में लिखी हैं तो **यह फेल होगा** — यही सीख है।
3. 🟢 क्रम ठीक कीजिए।

### चरण 5 — Refactor

1. हरे पर, शाखाओं को एक accumulator में समेटिए (`result = ""` फिर append)।
2. टेस्टों को एक parameterised table के रूप में दोबारा लिखिए।
3. चलाइए। अब भी हरा — आपने आकार बदला, व्यवहार नहीं।

> ✅ **तब पूरा:** जब पूरी suite एक table हो और implementation 8 लाइनों से कम।

## Kata 2 — String Calculator

**कठिनाई:** ★★☆☆☆ · **समय:** 30–45 मिनट · **क्या सिखाता है:** क्रमिक requirements, किनारे के मामले, अटकलों से बचना

_`add(numbers: str) -> int` लिखिए।_ Requirements **एक-एक करके** आती हैं — आगे मत पढ़िए।

### चरण 1 — ख़ाली और एकल

1. 🔴 `add("")` लौटाए `0`।
2. 🟢 `return 0`।
3. 🔴 `add("1")` लौटाए `1`।
4. 🟢 अब असली parsing।

### चरण 2 — दो संख्याएँ, फिर कई

1. 🔴 `add("1,2")` लौटाए `3`।
2. 🟢 comma पर split, फिर जोड़।
3. 🔴 `add("1,2,3,4,5")` लौटाए `15`। **अगर यह पहले से पास है, तो आपने सही सामान्यीकरण किया** — ठीक है, नोट कीजिए और आगे बढ़िए।

### चरण 3 — Newline भी separator

1. 🔴 `add("1\n2,3")` लौटाए `6`।
2. 🟢 दोनों delimiters संभालिए।
3. 🔵 अगर parsing शोर-शराबे वाली हो रही है तो एक `_split` helper अलग निकालिए।

### चरण 4 — मनचाहा delimiter

_Input `//;\n` से शुरू हो सकता है, जिसका मतलब है `;` delimiter है।_

1. 🔴 `add("//;\n1;2")` लौटाए `3`।
2. 🟢 Header parse कीजिए, फिर अपने मौजूदा split को काम सौंप दीजिए।
3. 🔵 ग़ौर कीजिए कि यह कितना आसान रहा, क्योंकि चरण 3 में parsing पहले ही अलग हो चुकी थी।

### चरण 5 — Errors

1. 🔴 `add("1,-2")` इस संदेश के साथ raise करे: `"negatives not allowed: -2"`।
2. 🟢 लागू कीजिए।
3. 🔴 `add("1,-2,-5")` **सभी** ऋणात्मक संख्याएँ गिनाए: `"negatives not allowed: -2, -5"`।
4. 🟢 पहले इकट्ठा कीजिए, फिर raise कीजिए।

### चरण 6 — बड़ी संख्याएँ नज़रअंदाज़ कीजिए

1. 🔴 `add("2,1001")` लौटाए `2` — 1000 से बड़ी संख्याएँ नज़रअंदाज़ होती हैं।
2. 🟢 Filter कीजिए।
3. 🔵 टेस्ट और production code दोनों पर आख़िरी refactor।

> ✅ **तब पूरा:** जब हर requirement एक फेरे में निपटी हो, और आपने ऐसी requirement के लिए कभी कोड न लिखा हो जो आपको दी ही नहीं गई थी।

## Kata 3 — Roman Numerals

**कठिनाई:** ★★★☆☆ · **समय:** 30 मिनट · **क्या सिखाता है:** algorithm को पहले से डिज़ाइन करने के बजाय उभरने देना

_1–3999 को रोमन अंकों में बदलिए।_

### चरण 1 — एक-एक करके

1. 🔴🟢 `1` → `"I"`। Hardcode कीजिए।
2. 🔴🟢 `2` → `"II"`।
3. 🔴🟢 `3` → `"III"`। अभी loop लिखने से बचिए।

### चरण 2 — पहला pattern

1. 🔴 `5` → `"V"`।
2. 🟢 जो भी पास करा दे।
3. 🔴 `6` → `"VI"`, फिर `8` → `"VIII"`।
4. 🔵 **अब** कोई pattern दिखना चाहिए। value→symbol table की ओर refactor कीजिए।

### चरण 3 — घटाव वाले मामले

1. 🔴 `4` → `"IV"`।
2. 🟢 तरकीब: उसी table में `4 → "IV"` एक entry के रूप में जोड़ दीजिए। किसी विशेष मामले की ज़रूरत नहीं।
3. 🔴 `9` → `"IX"`। वही चाल।

### चरण 4 — बड़ा कीजिए

1. 🔴🟢 `40`, `90`, `400`, `900`, `1000`।
2. 🔴 `1994` → `"MCMXCIV"`।
3. 🔵 अब implementation एक table और पाँच लाइनों का greedy loop होना चाहिए।

> ✅ **तब पूरा:** जब किसी ख़ास संख्या पर शाखा बनाने वाला कोई `if` न बचे — सिर्फ़ table।
>
> 💡 **सीख:** table लगभग कोई पहले से डिज़ाइन नहीं करता। अगर आप काफ़ी छोटे कदम लें तो यह चरण 2 के आसपास ख़ुद _उभर_ आता है।

## Kata 4 — Bank Account

**कठिनाई:** ★★★☆☆ · **समय:** 45 मिनट · **क्या सिखाता है:** state, invariants, सीमा पर test doubles

_जमा (deposit), निकासी (withdraw), statement छापना।_

### चरण 1 — Balance

1. 🔴 नए account का balance `0` हो।
2. 🔴🟢 `deposit(100)` → balance `100`।
3. 🔴🟢 `withdraw(30)` → balance `70`।

### चरण 2 — Invariants

1. 🔴 balance से ज़्यादा `withdraw` करने पर `InsufficientFunds` raise हो।
2. 🔴 `deposit(-5)` पर `ValueError` raise हो।
3. 🔴 `deposit(0)` — नियम तय कीजिए, फिर उसे कील ठोंकने वाला टेस्ट लिखिए।
4. 🔵 Validation अलग निकालिए।

### चरण 3 — घड़ी एक सीमा है

Statements को तारीख़ें चाहिए, और असली घड़ी टेस्टों को अनिश्चित बना देती है।

1. 🔴 `test_statement_shows_transaction_date` लिखिए — इसे एक _तय_ तारीख़ चाहिए।
2. 🟢 घड़ी inject कीजिए: `Account(clock=lambda: date(2026, 1, 15))`।
3. 🔵 ग़ौर कीजिए कि आपने क्या किया — एक बेक़ाबू dependency को parameter से बदल दिया। समय, randomness और IDs के लिए यही मानक चाल है।

### चरण 4 — Statement की सजावट

1. 🔴 ख़ाली account सिर्फ़ header पंक्ति छापे।
2. 🔴 एक deposit एक लाइन छापे, सही सजावट के साथ।
3. 🔴 कई transactions **उल्टे कालक्रम** में छपें।
4. 🔵 "क्या हुआ" (transaction सूची) को "कैसा दिखता है" (formatter) से अलग कीजिए। दो objects, अलग-अलग टेस्ट।

> ✅ **तब पूरा:** जब हर टेस्ट deterministic हो — कोई `date.today()` नहीं, कोई `random` नहीं, और suite किसी भी दिन किसी भी घंटे पास हो।

## Kata 5 — Bowling Game

**कठिनाई:** ★★★★☆ · **समय:** 45–60 मिनट · **क्या सिखाता है:** सचमुच पेचीदा logic में बहुत छोटे कदमों से काम करना

_दस-पिन गेंदबाज़ी (bowling) के खेल का स्कोर निकालिए। Strikes और spares आगे बोनस ले जाते हैं।_

### चरण 1 — Gutter game

1. 🔴 `0` की 20 rolls का स्कोर `0`।
2. 🟢 `return 0`।

### चरण 2 — सारे एक

1. 🔴 `1` की 20 rolls का स्कोर `20`।
2. 🟢 rolls का योग कीजिए।

### चरण 3 — एक spare

1. 🔴 `5, 5, 3` फिर सब शून्य → स्कोर `16`।
2. 🟢 Strikes को साथ में संभालने की कोशिश **मत** कीजिए। एक फेरे में एक नियम।
3. 🔵 अगर index का गणित पढ़ने में मुश्किल हो रहा है तो frame-आधारित iteration लाइए।

### चरण 4 — एक strike

1. 🔴 `10, 3, 4` फिर सब शून्य → स्कोर `24`।
2. 🟢 Strike वाली शाखा जोड़िए।

### चरण 5 — Perfect game

1. 🔴 `10` की 12 rolls का स्कोर `300`।
2. 🟢 यही वह टेस्ट है जो दसवें frame की off-by-one ग़लतियाँ पकड़ता है।
3. 🔵 आख़िरी सफ़ाई — `_is_strike`, `_is_spare`, `_frame_score` अलग निकालिए।

> ✅ **तब पूरा:** जब perfect game पास हो और कोड bowling के नियमों जैसा पढ़ा जाए।
>
> ⚠️ **जाल:** लगभग हर कोई चरण 3 के आसपास strikes और spares को एक ही छलाँग में हल करने की कोशिश करता है, 40 मिनट अटकता है, और सीखता है कि छोटे कदम क्यों होते हैं। एक बार यह ठोकर ख़ुद खाइए।

## अभ्यास कैसे करें

### चरण 1 — पहली बार

1. Kata 1 चुनिए। चरणों का ठीक वैसे ही पालन कीजिए जैसे लिखे हैं।
2. अपना समय नापिए। रफ़्तार के लिए नहीं — **कभी कोई red न छोड़ने** के लिए अनुकूलित कीजिए।

### चरण 2 — बंदिशों के साथ दोहराइए

जो kata आप पहले हल कर चुके हैं, उसे एक अतिरिक्त नियम के साथ दोबारा कीजिए:

| बंदिश                                    | किसका अभ्यास                     |
| ---------------------------------------- | -------------------------------- |
| **कोई `if` नहीं**                        | Polymorphism और lookup tables    |
| **हर method ≤ 3 लाइनें**                 | लगातार निकालते रहना (extracting) |
| **2 मिनट लाल रहने पर revert**            | सचमुच छोटे कदम                   |
| **कोई माउस नहीं**                        | अपने editor में प्रवाह           |
| **Ping-pong** (एक red लिखे, दूसरा green) | जोड़ी में काम (pairing)          |

### चरण 3 — इसे आदत बनाइए

1. हफ़्ते में एक kata, 30 मिनट।
2. इन्हें बारी-बारी से कीजिए — मक़सद दोहराव है, नयापन नहीं।
3. महीने में एक बार कोई kata **ऐसी भाषा में** कीजिए जो आपको ठीक से नहीं आती। इससे पता चलता है कि आपकी रफ़्तार में कितना आदत है और कितनी समझ।
