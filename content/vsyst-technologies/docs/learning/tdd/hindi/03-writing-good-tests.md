# 3. अच्छे टेस्ट लिखना

Test suite तब तक संपत्ति है जब तक वह बोझ न बन जाए। फ़र्क़ कारीगरी का है।

## संरचना: Arrange, Act, Assert

हर टेस्ट के तीन हिस्से होते हैं। उन्हें देखने में अलग-अलग रखिए।

```python
def test_discount_applies_to_orders_over_100():
    # Arrange — दुनिया तैयार कीजिए
    cart = Cart()
    cart.add(Item("desk", price=120))

    # Act — जो एक चीज़ टेस्ट हो रही है, वह कीजिए
    total = cart.total()

    # Assert — नतीजा जाँचिए
    assert total == 108  # 10% छूट
```

अगर आपका **Arrange** हिस्सा बहुत बड़ा है, तो यह डिज़ाइन की बदबू है — जिस चीज़ को टेस्ट कर रहे हैं उसे शायद अस्तित्व में आने के लिए बहुत कुछ चाहिए।

अगर आपके पास **कई Act** हैं, तो शायद एक ही टेस्ट में कई टेस्ट छिपे हैं।

## नामकरण

नाम से पता चलना चाहिए कि लाल होने पर क्या टूटा है, ताकि आप CI का output पढ़कर ही समझ जाएँ और फ़ाइल खोलनी न पड़े।

| ❌ ख़राब        | ✅ अच्छा                                    |
| --------------- | ------------------------------------------- |
| `test_cart`     | `test_empty_cart_total_is_zero`             |
| `test_1`        | `test_expired_coupon_is_rejected`           |
| `test_it_works` | `test_negative_quantity_raises_value_error` |

एक टिकाऊ pattern: **`test_<स्थिति>_<अपेक्षित नतीजा>`**।

## फेल होने का एक ही कारण

हर टेस्ट एक ही व्यवहार जाँचे। ज़रूरी नहीं कि एक ही assertion हो — पर फेल होने का _कारण_ एक हो।

```python
# ठीक है: कई assertions, पर व्यवहार एक ही
def test_new_user_starts_with_empty_profile():
    user = User("ada")
    assert user.name == "ada"
    assert user.posts == []
    assert user.verified is False
```

```python
# ठीक नहीं: एक ही टेस्ट में तीन असंबंधित व्यवहार
def test_user_stuff():
    assert User("ada").name == "ada"
    assert login("ada", "wrong") is False
    assert delete_user("ada") is True
```

जब दूसरा वाला लाल होगा, तब तक आपको पता नहीं चलेगा कि क्या टूटा है जब तक पूरा पढ़ न लें।

## व्यवहार टेस्ट कीजिए, implementation नहीं

आपकी suite समय के साथ टिकेगी या नहीं — इस पर सबसे बड़ा असर इसी बात का है।

```python
# ❌ internals से जुड़ा — private field का नाम बदलते ही टूट जाएगा
def test_add_item():
    cart = Cart()
    cart.add(Item("pen", 2))
    assert cart._items[0]._price == 2

# ✅ व्यवहार से जुड़ा — refactoring झेल जाएगा
def test_add_item():
    cart = Cart()
    cart.add(Item("pen", 2))
    assert cart.total() == 2
```

**कसौटी:** अगर आप internals पूरी तरह दोबारा लिख दें पर व्यवहार वही रखें, तो क्या आपके टेस्ट फिर भी पास होंगे? अगर सब टूट जाएँ, तो वे ग़लत चीज़ टेस्ट कर रहे थे — और जब भी आप कोड सुधारने चलेंगे, वे अड़ंगा डालेंगे।

## क्या टेस्ट करें

**ज़रूर करें:**

- कारोबारी नियम (business rules) और गणनाएँ
- किनारे के मामले — ख़ाली, शून्य, एक, बहुत सारे, ऋणात्मक, null, बहुत बड़े
- ग़लती के रास्ते — कचरा input मिलने पर क्या होता है
- वे बग जो आपने ठीक किए (पहले फेल होता टेस्ट लिखिए, _फिर_ ठीक कीजिए — यह भी TDD है)

**इनके पीछे मत पड़िए:**

- भाषा या standard library
- तीसरे पक्ष के frameworks (उनका नहीं, _आपके उनके इस्तेमाल_ का टेस्ट कीजिए)
- बिना logic वाले मामूली getters और setters
- log संदेशों के ठीक-ठीक शब्द, जिन पर कोई assert नहीं करता

## टेस्ट तेज़ रखिए

धीमे टेस्ट छोड़ दिए जाते हैं। छोड़े गए टेस्ट बेकार हैं।

लक्ष्य रखिए कि unit suite **सेकंडों** में चले। असली databases, network calls और `sleep()` तभी इस्तेमाल कीजिए जब आप सचमुच integration टेस्ट कर रहे हों — और उन्हें एक अलग, धीमी परत में रखिए जिसे कम बार चलाएँ।

```
      /\        थोड़े, धीमे, ऊँचा भरोसा
     /  \       End-to-end
    /----\
   /      \     Integration
  /--------\
 /          \   Unit — बहुत सारे, तेज़, सस्ते
/____________\
```

आकार को लेकर कट्टर होने की ज़रूरत नहीं, पर सिद्धांत सही है: आपकी ज़्यादातर feedback तेज़ परत से आनी चाहिए।

## टेस्ट का नतीजा हर बार एक-सा हो (deterministic)

बीस में से एक बार फेल होने वाला टेस्ट, कोई टेस्ट न होने से भी बुरा है — वह सबको लाल रंग नज़रअंदाज़ करना सिखा देता है।

आम दोषी:

- असली घड़ी (`now()`) → समय को inject कीजिए
- Random मान → seed कीजिए, या ठीक मान की जगह गुणों पर assert कीजिए
- टेस्टों के बीच साझा state → हर टेस्ट अपनी दुनिया ख़ुद बनाए
- टेस्ट के क्रम पर निर्भरता → टेस्ट किसी भी क्रम में, और अकेले भी पास होने चाहिए
- असली network → सीमा (boundary) पर stub लगाइए

## हद से ज़्यादा mock मत कीजिए

Mocks असली सीमाओं पर काम के हैं: network, filesystem, घड़ी, payment providers।

बाक़ी सब कुछ mock कर दीजिए और अंत में आप बस यह जाँच रहे होंगे कि आपका कोड उन्हीं functions को बुलाता है जिन्हें बुलाने के लिए आपने लिखा था — यानी ऐसा टेस्ट जो असली व्यवहार कितना भी टूटा हो, पास ही रहेगा।

> मोटा नियम: जो चीज़ें आपकी **नहीं** हैं, उन्हें mock कीजिए। जो आपकी हैं, उनके लिए असली चीज़ इस्तेमाल कीजिए।
