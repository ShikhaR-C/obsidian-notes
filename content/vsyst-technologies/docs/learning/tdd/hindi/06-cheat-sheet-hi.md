# 6. चीट शीट

## चक्र

| कदम             | करें                                                       | न करें                                           |
| --------------- | ---------------------------------------------------------- | ------------------------------------------------ |
| 🔴 **Red**      | एक छोटा फेल होता टेस्ट लिखें। चलाएँ। फ़ेल्योर संदेश पढ़ें। | अभी production code मत लिखें।                    |
| 🟢 **Green**    | सबसे आसान चीज़ लिखें जो पास करा दे — hardcoding चलेगी।     | कल्पित भविष्य की ज़रूरतों के लिए मत बनाइए।       |
| 🔵 **Refactor** | दोहराव हटाएँ, नाम बदलें, आसान करें। टेस्ट हरे रहें।        | नया व्यवहार मत जोड़िए। लाल पर refactor मत कीजिए। |

**लक्ष्य: एक फेरा 2–10 मिनट में।** 15+ मिनट से लाल → हरे पर लौटिए, छोटा निवाला लीजिए।

---

## तीन नियम (Uncle Bob के शब्दों में)

1. जब तक फेल होता टेस्ट न हो, कोई production code मत लिखिए।
2. टेस्ट उतना ही लिखिए जितने से वह फेल हो जाए।
3. Production code उतना ही लिखिए जितने से टेस्ट पास हो जाए।

## टेस्ट का ढाँचा

```python
def test_<situation>_<expected outcome>():
    # Arrange
    ...
    # Act
    result = ...
    # Assert
    assert result == expected
```

## हर टेस्ट के लिए चेकलिस्ट

- [ ] क्या मैंने पहले इसे फेल होते देखा?
- [ ] क्या फ़ेल्योर संदेश शुक्रवार शाम चार बजे काम आएगा?
- [ ] क्या नाम बताता है कि क्या टूटा?
- [ ] फेल होने का एक ही कारण?
- [ ] व्यवहार, internals नहीं?
- [ ] अकेले, और किसी भी क्रम में पास होता है?
- [ ] तेज़ — कोई sleep नहीं, असली network नहीं?
- [ ] Deterministic — असली घड़ी नहीं, बिना seed की randomness नहीं?

## बदबू (smells) और उनका मतलब

| बदबू                        | संभावित कारण                                                     |
| --------------------------- | ---------------------------------------------------------------- |
| बहुत बड़ा Arrange हिस्सा    | जिसे टेस्ट कर रहे हैं उसे बहुत कुछ चाहिए; बहुत सारी dependencies |
| हर refactor पर टेस्ट टूटना  | internals टेस्ट हो रहे हैं, व्यवहार नहीं                         |
| ढेर सारे mocks              | बहुत सारे collaborators, या अपने ही कोड का mocking               |
| अस्थिर (flaky) टेस्ट        | समय, randomness, साझा state, या टेस्ट का क्रम                    |
| टेस्ट का नाम `test_thing_2` | एक ही टेस्ट में दो व्यवहार ठूँसे गए                              |
| टेस्ट लिखना ही मुश्किल हो   | डिज़ाइन आपको कुछ बता रहा है — सुनिए                              |

## TDD कब इस्तेमाल करें

**हाँ:** business rules · गणनाएँ · parsing · state machines · किनारे के मामलों से भरा कोड · बग फ़िक्स · कुछ भी जो लंबा चलेगा

**शायद नहीं:** फेंकने वाले prototypes · वे spikes जो मिटा देंगे · pixel layout · generated code · मामूली config

## काम के commands

```bash
# Python
pytest                          # सब चलाएँ
pytest -k "discount"            # मेल खाते टेस्ट चलाएँ
pytest --lf                     # पिछली बार के फ़ेल्योर दोबारा चलाएँ
pytest -x                       # पहले फ़ेल्योर पर रुक जाएँ
pytest -q --tb=short            # शांत output, छोटे tracebacks

# JavaScript / TypeScript
npx vitest --watch              # save पर दोबारा चलाएँ
npx jest --watch
npx jest -t "discount"

# Go
go test ./... -run TestDiscount
```

TDD करते समय अपनी suite **watch mode** में चलाइए। यह चक्र तभी सुखद है जब feedback तुरंत मिले।
