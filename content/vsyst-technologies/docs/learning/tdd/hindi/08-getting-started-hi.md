# 8. शुरुआत कैसे करें

इसे असल में शुरू कैसे करें — नए प्रोजेक्ट पर, पुराने पर, और ऐसी टीम के साथ जो अभी राज़ी नहीं हुई है।

## पहले टेस्ट से पहले

ये दो चीज़ें ठीक कर लीजिए, वरना बाक़ी कुछ नहीं टिकेगा:

**1. Suite तेज़ बनाइए।** पूरी suite एक मिनट से कम में, और जिन टेस्टों पर आप काम कर रहे हैं वे एक सेकंड से कम में। धीमी suites छोड़ दी जाती हैं; छोड़ी गई suites बेकार हैं।

**2. उसे watch mode पर लगाइए।** यह चक्र तभी सुखद है जब feedback तुरंत मिले। स्क्रीन बाँट लीजिए — एक तरफ़ कोड, दूसरी तरफ़ हर save पर दोबारा चलता test runner।

```bash
pytest-watch              # Python
npx vitest                # JS/TS (watch डिफ़ॉल्ट है)
dotnet watch test         # C#
gotestsum --watch         # Go
```

शून्य से runner चलाने के लिए देखिए [भाषा के अनुसार सेटअप](09-language-setup-hi.md)।

---

## आपका पहला हफ़्ता

पूरा workflow बदलने की कोशिश मत कीजिए। एक सीमित आदत चुनिए और तब तक कीजिए जब तक वह अपने आप न होने लगे।

### दिन 1–2: सिर्फ़ बग फ़िक्स

अगला बग मिले, तो कुछ भी ठीक करने से पहले:

1. ऐसा टेस्ट लिखिए जो उसे दोहराए। उसे फेल होते देखिए।
2. बग ठीक कीजिए।
3. उसे हरा होते देखिए।

यह सबसे आसान प्रवेश-द्वार है। अपेक्षित व्यवहार आपको पहले से पता है, दायरा बहुत छोटा है, और कोई यह नहीं कहेगा कि regression test समय की बर्बादी थी।

### दिन 3–4: एक नया function

अगला शुद्ध logic का टुकड़ा चुनिए जो आपको लिखना है — कोई गणना, कोई validator, कोई parser। ऐसा कुछ जिसमें input और output हों और कोई database न हो।

पूरा चक्र कीजिए। पहले implementation लिखने की इच्छा को दबाइए। यह धीमा और थोड़ा बेवक़ूफ़ी भरा लगेगा। यह सामान्य है और गुज़र जाता है।

### दिन 5: टेस्ट के नीचे किसी चीज़ को refactor कीजिए

ऐसा कोड लीजिए जिसके टेस्ट पहले से हैं और उसका ढाँचा बदलिए — कोई function अलग निकालिए, नाम बदलिए, कोई परत हटाइए। टेस्ट चलाइए।

यही वह कदम है जहाँ TDD एक सैद्धांतिक बहस से हटकर _साफ़ तौर पर फ़ायदेमंद_ लगने लगता है। इसे एक बार महसूस करना ज़रूरी है।

---

## बिल्कुल नए प्रोजेक्ट पर शुरुआत

सबसे आसान मामला। दो नियम:

- पहला टेस्ट **production code की पहली लाइन से पहले** लिखिए — यहाँ तक कि folder ढाँचे से भी पहले। इससे आपको पहले ही दिन runner सेट करना पड़ेगा, जब यह सस्ता है।
- बाहर से शुरू कीजिए: इस चीज़ का इस्तेमाल करने वाला क्या बुलाना चाहेगा? API को टेस्ट तय करने दीजिए।

---

## बिना टेस्ट वाले मौजूदा codebase पर शुरुआत

पूरे कोड में टेस्ट पीछे से ठूँसने की कोशिश **मत** कीजिए। यह एक विशाल प्रोजेक्ट है जिसमें प्रगति दिखती नहीं, और यह हमेशा बीच में अटक जाता है।

बजाय इसके, जिस काम पर आप वैसे भी लगे हैं, उसी के इर्द-गिर्द टेस्ट वाले हिस्से को बढ़ने दीजिए:

### कदम 1 — मौजूदा व्यवहार को कील ठोंकिए

**Characterization tests** लिखिए: ऐसे टेस्ट जो पकड़ लें कि कोड _अभी_ क्या करता है, भले ही वह ग़लत ही क्यों न हो।

```python
# यह assert नहीं कर रहे कि यह सही है — बस यह कि आज यही होता है।
def test_legacy_pricing_current_behaviour():
    assert calculate_price(qty=3, code="LEGACY") == 27.5
```

अब आपके पास एक जाल है। आप बिना चुपचाप व्यवहार बदले refactor कर सकते हैं।

पता नहीं यह क्या लौटाता है? चला कर देख लीजिए, फिर वह मान चिपका दीजिए। यहाँ यह जायज़ है।

### कदम 2 — कोई seam ढूँढ़िए

आम अड़चन यह होती है कि जिस कोड को आप टेस्ट करना चाहते हैं वह सीधे किसी database, घड़ी, या HTTP call तक पहुँच जाता है। सबसे छोटा बदलाव ढूँढ़िए जिससे आप उन्हें बदल सकें — उसे argument के रूप में भेजिए, या किसी interface के पीछे छिपा दीजिए।

### कदम 3 — आगे से यह नियम लागू कीजिए

- हर **बग फ़िक्स** पहले एक फेल होते टेस्ट के साथ आए।
- हर **नया** logic का टुकड़ा test-first लिखा जाए।
- जिस कोड को आप छूते नहीं, वह बिना टेस्ट रहे। कोई बात नहीं।

कुछ महीनों बाद codebase के जो हिस्से सबसे ज़्यादा बदलते हैं — यानी जो मायने रखते हैं — वही हिस्से टेस्ट वाले होंगे।

> 📖 Michael Feathers की _Working Effectively with Legacy Code_ पूरी किताब इसी पर है, और अगर आपकी यही स्थिति है तो पढ़ने लायक़ है।

## "अच्छा चल रहा है" कैसा लगता है

आपको पता चल जाएगा कि यह काम कर रहा है जब:

- आप शायद ही कभी हरी suite से कुछ मिनटों से ज़्यादा दूर होते हैं
- आप पहले से कहीं कम debugger खोलते हैं
- आप बिना पेट में गाँठ के refactor करते हैं
- लाल टेस्ट का सिर्फ़ नाम पढ़कर पता चल जाता है कि क्या ग़लत है
- कोई अलग नतीजे की उम्मीद में CI दोबारा नहीं चलाता

## "गड़बड़ हो रही है" कैसा लगता है

- Suite इतना समय लेती है कि आप उसे चलाना बंद कर देते हैं
- हर refactor के बाद आप बीस टेस्ट ठीक करते हैं → [internals टेस्ट हो रहे हैं](03-writing-good-tests-hi.md)
- टेस्ट कभी-कभी फेल होते हैं और सब कंधे उचका देते हैं → [अस्थिरता](05-pitfalls-and-faq-hi.md)
- आप coverage का gate पार करने के लिए कोड के बाद टेस्ट लिखते हैं → वह gate नुक़सान कर रहा है; उसे हटाने की बात कीजिए

## अपनाने लायक़ टीम की आदतें

**Build हरी रखिए।** हमेशा लाल रहने वाली main branch सबको फ़ेल्योर नज़रअंदाज़ करना सिखा देती है। अगर वह लाल हो जाए, तो उसे ठीक करना सबसे बड़ी प्राथमिकता है।

**सिर्फ़ कोड नहीं, टेस्ट भी review कीजिए।** Pull request में पहले टेस्ट के नाम पढ़िए। अगर उनसे यह पता नहीं चलता कि बदलाव क्या करता है, तो बेहतर नाम माँगिए।

**जो टेस्ट अपना किराया नहीं दे रहे, उन्हें हटा दीजिए।** टेस्ट भी कोड हैं और उनका रखरखाव-खर्च है। जो टेस्ट comment कर दिया गया है, या कुछ assert नहीं करता, या किसी दूसरे की नक़ल है — हटा दीजिए। भरोसे वाली छोटी suite, अविश्वसनीय बड़ी suite से बेहतर है।

**Coverage का लक्ष्य मत तय कीजिए।** Coverage से खाली जगहें ढूँढ़िए और तय कीजिए कि वे मायने रखती हैं या नहीं। जिस पल यह एक आँकड़ा बन जाता है जिस पर लोगों को नापा जाता है, आपको ऐसे टेस्ट मिलने लगते हैं जो व्यवहार जाँचने के बजाय लाइनें छूने के लिए लिखे जाते हैं।

**शुरुआत में जोड़ी बनाकर (pair) कीजिए।** TDD पढ़कर सीखने से कहीं आसान है किसी को एक घंटा करते हुए देखकर सीखना — इस दस्तावेज़ को पढ़ने से भी।
